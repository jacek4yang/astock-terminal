# Upgrading from v6.0.0 to v7.0.0

v7 replaces the production Agent implementation. Orchestration moves from the
MoonBit Agent worker running under the Proton/CEF host to the Rust
`astock-agent-runtime`, and the desktop host becomes a thin Tauri v2 adapter.

Your data is preserved. Conversation history, evidence, market caches and stored
credentials all carry forward. What does **not** carry forward is the executable
state of a task that was mid-flight under the retired reducer, for reasons
explained below.

## What happens on first launch

Nothing is required of you. The Engine opens the existing data root and applies
any pending schema migrations automatically.

| Data | Behaviour |
| --- | --- |
| Conversation history | Preserved and readable. |
| Evidence archive, source revisions | Preserved. |
| Market and K-line caches | Preserved. |
| Graph data | Preserved. |
| Settings (`config.toml`) | Preserved; no v7 key is required. |
| Stored credentials | Preserved on Windows and macOS. See the Linux note below. |
| **In-flight task execution state** | Archived, not resumed. A new task is started instead. |

## Why an interrupted v6 task is not resumed

A durable task records a phase, an accepted-sequence cursor and a set of
completed effects. Those values are only meaningful to the reducer that wrote
them. Adopting a v6 projection into the Rust runtime could make it skip work it
never performed, or repeat an external effect it had already completed — the
exact failure the effect-ordering rules exist to prevent.

So v7 fails closed. A conversation is read, its messages are preserved, and any
task projection that is not the Rust runtime's own shape is discarded rather than
resumed. Ask your question again and the Agent starts a fresh task with the full
prior conversation still in context.

A record that claims a session version the runtime does not know is refused
outright with `unsupported session version` rather than being interpreted
optimistically.

This is covered by `crates/agent-runtime/tests/migration_v6_to_v7.rs`:

- a v6 conversation with no task projection stays readable and validates;
- a v6 conversation carrying the retired reducer's projection never yields v7
  executable state, while its history survives;
- an unknown session version is refused and names the cause;
- a session recorded before plans existed loads with no plan invented and its
  effect cursor intact.

## Schema migrations

SQLite migrations are numbered and tracked in the `user_version` pragma, applied
in a single transaction, so a failure leaves the pre-upgrade version intact and
re-running is idempotent. A verified backup is taken before the upgrade.

## Credentials

Windows Credential Manager and macOS Keychain entries carry forward unchanged.

On Linux, v7 stores credentials in the kernel keyutils keyring. That is real
storage but it is session-scoped: it is cleared on logout or reboot, so you will
be prompted again after a fresh login. Earlier builds enabled only the Windows
backend, which meant Linux and macOS silently used an in-memory mock where
storing a key reported success and the value was never persisted; if you relied
on that, the credential was never actually saved and must be installed again:

```bash
astock credentials set minimax
astock credentials set joinquant   # optional
astock credentials status          # presence only, never prints a value
```

Cross-reboot persistence on Linux needs the D-Bus Secret Service backend
(gnome-keyring or kwallet). That is deliberately not enabled yet because it adds
a libdbus system dependency that cannot be verified headlessly.

## Two data roots, or one

The terminal and the desktop share one data root by default, so a session started
in one is visible in the other. Both honour an explicit override, which is useful
for a portable install or separate research profiles:

```bash
astock --data-dir /path/to/root ...
ASTOCK_DATA_DIR=/path/to/root astock ...
```

A relocated root keeps durable data and cache in separate subdirectories, so
clearing a cache can never remove evidence or sessions.

## Downgrading

v6.0.0 remains published and its tag is immutable. Because v7 migrations may bump
the schema `user_version`, a v6 binary opened against a v7-migrated data root is
not supported. If you need to return to v6, restore the pre-upgrade backup that
the migration wrote.

## What is not part of this upgrade

The Proton/CEF host, the MoonBit worker, the TLA+ specifications and the v6
publication scripts all remain in the repository as historical, specification and
formal-verification assets. They are no longer the production path and are not
installed by the v7 package.
